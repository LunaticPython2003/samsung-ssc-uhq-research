# R640 886-kbps E4 receiver: instruction-level re-audit

**Date:** 2026-11-04 (Asia/Kolkata).
**Input:** Samsung Galaxy Buds4 Pro (SM-R640) firmware `R640XXU0AZD2`, SHA-256 `b91289cd445449485087aa380559eea167e5c0009ecdb912139d11212e02749f`.
**Scope:** read-only static analysis of locally downloaded proprietary firmware, plus original Galaxy Z Fold7 software encoder/BT stack; no flashing, pairing, radio injection, or modification to earbuds.
**Tools:** Capstone 5 / Ghidra 12.2, independently cross-checking raw ARM Thumb-2 instruction bytes, stored locally in `tools/ghidra-runs/r640-verify-dispatch.log`.
**Reproduce:** `python3 scripts/audit-r640-receiver.py` and `python3 -m unittest -v test_ssc_r640_receiver.py`. Original firmware lives in gitignored `vendor-local/buds-fw/` and is NOT redistributed.

## Most important correction to our earlier conclusion

We previously stated that because `E4` is absent from the UHQ pre-parser's three-way branch, the receiver rejects all 886-kbps frames. **That was too strong.**

1. The firmware's **initial validator** may *accept* an E4 frame: E4 routes to a generic **484-byte minimum** length check; a full 1000-byte E4 frame is long enough.
2. The next SSC UHQ **sequence/packet pre-parser** only has dedicated `E0`, `E3` and `E6` handling. It immediately returns for E4. **But its direct caller ignores the return register**, continuing into a shared dispatch path.
3. A **separate SSC receive queue/validation function** caps its incoming payload to **800 bytes** before copying and calling the validator. A 1000-byte encoder-produced E4 frame could not reach that validator intact *through this particular path* without a separate fragmentation/reassembly layer, which was **not** established.
4. The **downstream decoder/DSP** has not been fully reverse-engineered. It is therefore unsupported to assert that the physical Buds4 Pro can never play E4, or that another firmware/transport path cannot carry it.

This is evidence against a straightforward single-packet E4 path on this firmware, **not a global proof of rejection**. E4 remains encoder-confirmed, receiver-playback unverified.

## 1. Switch lowering: raw Thumb-2 TBB

Ghidra identifies a computed jump instruction at file offset `0x8D992`: `tbb [pc,r3]`. A bounds check `cmp r3,#0x16 / bhi 0x8D9BC` precedes it. `r3 = frame[3]&0x1F`.

Raw TBB unsigned-byte table starts at `0x8D996` and uses destination `0x8D996 + 2*table[index]`. Independently verified by Capstone/Ghidra:

| Frame nibble | Jump offset | Minimum length in first validator |
| --- | --- | ---: |
| E0 (0) | `0x8D9EE` | 330 |
| E1 (1) | `0x8D9BC` | 484 |
| E2 (2) | `0x8D9BC` | 484 |
| E3 (3) | `0x8D9F8` | 660 |
| **E4 (4)** | **`0x8D9BC`** | **484** |
| E5 (5) | `0x8D9BC` | 484 |
| E6 (6) | `0x8DA02` | 174 |

The default branch at `0x8D9BC` loads `0x1E4=484`; if length >= threshold it sets `r0=1` and returns. Thus E4 is *not* explicitly rejected at this stage.

Additional standard-family types F0/F1/F2/F4/F5/F6 have distinct cases; this switch is NOT purely a UHQ codec-rate table.

## 2. Caller and return semantics

In the UHQ pre-parser beginning at `0x8AFD4`, the header sync `FF` and E-class high nibble `E0` are tested. It checks `frame[3]&0x1F`:

- E0 takes the main branch.
- E3 joins the main branch.
- E6 takes a separate short-frame branch.
- Other types including E1/E2/**E4**/E5 go to an early stack unwind at `0x8B00E`.

A call at `0x17BBCE` invokes this pre-parser; the **very next instruction** at `0x17BBD2` reloads a state byte without comparing the function's return value. Control branches to `0x17B01E` and calls additional state/dispatch functions at `0x17B022` and `0x17B034`. No claim is made here that these calls successfully deliver a complete E4 frame to the DSP. Their semantics require separate runtime tracing.

The first validator has its own caller: `0x8DEF2` calls the validator, `0x8DEF6` tests the returned boolean, and the *successful* path continues with queue management. This confirms the initial success for E4 is potentially meaningful to the packet queue, rather than simply falling out.

## 3. New 800-byte SSC receive-queue limit

Another receiver-side function at file offset `0x8DE50` takes its incoming payload length in `r2` and saves it into `r10` at `0x8DE5A`.

- `0x8DEB4`: compare `r10` with `0x320 = 800`.
- `0x8DEB8`: if greater, branch to `0x8E014`.
- `0x8E014..0x8E01E`: replace active length with 800 bytes and return to normal allocation path.
- `0x8DEBC`: allocate an 800-byte buffer.
- `0x8DED0..0x8DEE8`: copy `r10` bytes using the capped value.
- `0x8DEF2`: invoke SSC frame validator on the queued/capped data.

The cap is based on actual ARM instructions independently checked in Ghidra. The original Fold7 UHQ E4 encoder returns **1,000 bytes** per 864-sample frame, compared with **660 bytes** for E3. Through this queue, a 1,000-byte frame would be **truncated by 200 bytes**.

The queue function is not referenced by a direct BL in the scan; registration through an indirect callback or other entry mechanism remains possible. We have **not** proved that every active SSC audio path goes through this exact queue, nor established any separate E4 reassembly logic.

The earlier reported Buds4 Pro peer MTU = **1005 bytes** introduces an additional conditional limit: if RTP-inclusive, the minimal E4 packet needs 1000+12=**1012 bytes**, seven more than 1005 even before extra headers. Actual MTU accounting/reassembly must be captured on a live connection to settle this.

## 4. DSP/second-core investigation

The R640 firmware archive is an 8,968,784-byte raw Bestechnic/ARM container. It contains distinct `SSC UHQ ssc_decoder_init` and `M55C0-DSPC0` diagnostic strings, plus multiple code/data regions. This is credible evidence of a separate DSP/core component, but the complete core mapping and any DSP-side E4 bit-allocation table are **not reconstructed**. A string alone is not a decoder implementation.

We compared the R630 (Buds3 Pro) April 2026 firmware region previously described as decoder data at file offsets `0x3C1A6C..0x3C2A00` with R640. Among **105** nontrivial 64-byte sample windows, **97** (92.4%) are identical within R640; **72** share one consistent relocation shift. Eight windows did not match. This supports substantial continuity in decoder-associated data but **does not prove identical executable decoder behavior or E4 absence**.

Searching the R640 firmware for a nearby *cluster* of literal 16/32-bit frame lengths **174, 330, 660 and 1000** found **no such cluster within 128 bytes of a 1000-byte entry**. That is negative evidence only: tables may be computed, packed, relocated, or held in DSP firmware.

Result: no verifiable DSP E4-specific support *or complete exclusion* established. Further decoder-core extraction/decompilation or a controlled radio test is required.

## 5. Capability negotiation

R640 A2DP vendor codec configuration function at `0x17AC54` reads:
- the 32-bit Samsung vendor ID, checks `0x75` at `0x17AC78`;
- the 16-bit codec ID, checks `0x0103` at `0x17AC7C`;
- one SSC feature/sample-rate byte at offset +6; applies masks and maps it to sample-rate and mode fields.

A standalone static vendor CIE sequence at firmware offset `0x441534` begins `75 00 00 00 03 01 3E`, with vendor ID 0x75, codec ID 0x0103 and **sample/feature candidate byte 0x3E**. This is a **firmware constant**, not proven to be the actual AVDTP capability returned to the user's phone and not evidence of E4 support. 0x3E lacks the earlier known 96-kHz bit 0x80; it may describe a default/legacy configuration.

Critically, the vendor capability byte encodes sample/mode features, **not an explicit list of encoder E0/E1/E2/E3/E4 frame-rate tags**. Therefore not finding E4 in capability bytes cannot itself show the receiver refuses E4. Live AVDTP discovery and SET_CONFIGURATION traces remain necessary.

## 6. Phone-side E4 selection

Samsung Fold7 `libbluetooth_jni.so` decompiled `a2dp_vendor_ssc_send_frames` contains a 96-kHz branch. When UHQ2 mode state is active (sample-rate=96000 and an internal UHQ2 flag is 1), its bitrate target comes from `0x002077B0`, with levels clamped to index <=3:

`[584000, 584000, 291000, 152000]`.

In another 96-kHz branch without that UHQ2 flag, the selected target is **328000**. The standard lower-rate tables are separate. When target bitrate changes, encoder state is updated via callback.

**No condition within this inspected sender branch selects 886000, and no device-model/ID check enabling E4 was found there.** This is not a proof that no other sender or firmware/driver can request E4. Samsung's private encoder `get_header_from_bitrate(886000)` does recognize 886k and produces valid-looking 1000-byte E4 frames. The gap is between *encoder API capability* and *sender/receiver negotiated operation*.

## 7. Empirical state and next gate

**Physical Buds4 Pro are available**, and the user's rooted Fold7 can encode real SSC E4 frames. A Linux encoder-to-provisional-RTP socket loopback has tested E4 frames successfully at a **hypothetical 1200-byte MTU**. No real Linux-host-to-Buds A2DP SSC injection has yet been accomplished: CatDesk Personal shell cannot access the host system D-Bus; the user's normal desktop can. The real BlueZ A2DP endpoint/transport negotiation and MTU must be established first.

The user offered to connect their earbuds to Linux. That is the next required action. Use read-only `python3 linux/ssc_bluez_probe.py`, then configure an authorized short, low-volume test after first proving **584-kbps E3** playback. Do **not** assume unverified E4 fragmentation or send malformed frames, and do not alter earbud firmware.

**Final characterization:** E4 is *encoder-proven*, *initial-validator-accepted*, *not processed by one UHQ pre-parser*, and *oversized for one receiver queue*. DSP and other fallback paths remain *unverified*. Absolute universal rejection is **not proven**, but simple single-packet E4 playback has substantive obstacles.

## Numeric sanity check

Raw 24-bit, 96-kHz stereo PCM = 4,608,000 bit/s. Compression ratios are 30.32:1 (152k), 15.84:1 (291k), 7.89:1 (584k), 5.20:1 (886k). The progression is coherent and E4 deliberate, but this does **not** prove it was intended for the SM-R640 receiver.
