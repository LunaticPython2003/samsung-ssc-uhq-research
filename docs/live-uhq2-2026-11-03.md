# SSC UHQ2 live playback findings — 2026-11-03

## Verified source
Galaxy Z Fold7 (SM-F966B), Android 17, rooted through ADB. The user enabled developer HCI logging and played Apple Music on Galaxy Buds4 Pro. No radio, Bluetooth pairing, firmware, or settings were modified by the research scripts.

## Real playback observations
- Android audio policy selected AUDIO_DEVICE_OUT_BLUETOOTH_A2DP for an active audio stream, rather than LE Audio.
- Samsung Bluetooth history showed both SSC HIFI and SSC UHQ2 capabilities; the runtime logs below confirm actual SSC operation independently.
- SSC stack logged encoder operations at sample 96000, stereo, frame count generally 1, with encoder level 1 after startup.
- HAL selected configuration: codec SSC, 96000 Hz, STEREO, bitsPerSample enum 34 (Samsung 8_24 representation; not 34-bit audio), encodedAudioBitrate 584000 bps, peerMtu 1005 bytes, SCMS-T disabled.
- HAL reported IsCodecOffloadingEnabled: enabled SSC. This reports the HAL state, not whether each operation runs in the DSP.
- Encoder update confirmed is_uhq2=true, bitrate_limitation=false.
- Real bitrate transition at 17:11:36.823: 0 -> 291000; 17:11:36.873: 291000 -> 584000 (50 ms apart).
- An audio stream restart around 17:12:07 selected 584000 from 0 immediately, and later logs continued at 96000 Hz level 1.
- No conclusive data about the actual source track's format; Android may resample the 16/44.1 to 24/96 Apple Music source before Bluetooth.

## Exact Windows-to-Samsung encoder reproduction
Tested with synthetic audio. ARM64 Samsung software encoder reached through a Windows-native Rust client over ADB localhost forwarding. This is **not** Windows Bluetooth transmission.

| Rate | Bit depth | Stereo samples/channel | Selected bitrate | Returned frame bytes |
|---|---|---|---|---|
| 96000 | 24 | 864 | 291000 | 330 |
| 96000 | 24 | 864 | 584000 | 660 |

Two direct ARM64 frames per mode succeeded with intact buffer canaries. The Windows Rust live_tone example processed eight more 584000-bps frames and returned 660 bytes for every one. Code: ssc-win-bridge/examples/live_tone.rs.

Using the reported MTU of 1005 and subtracting at least the 12-byte RTP header leaves 993 bytes before any extra SSC media header. Thus both 330- and 660-byte complete encoder frames fit the preliminary size budget. Actual packet framing, additional headers, and precise MTU accounting are not verified.

## HCI trace investigation
- Searched usual protected on-device Bluetooth log paths; no ordinary btsnoop file was found.
- Acquired a 52 MB adb bugreport into the local project. ZIP contained 380 entries but no independent HCI/btsnoop packet capture.
- Main dumpstate text included Samsung snoop_logger.cc compression and Base64 diagnostic activity; this does not prove an exportable packet stream was available.
- Deleted the unredacted bugreport ZIP immediately after analysis; unrelated personal diagnostics were not retained in the workspace.

## What remains unknown
- The AVDTP vendor codec ID actually negotiated with the Buds. Samsung's A2DP_ParseInfoSsc checks VID 0x75 and codec ID 0x0103, while a static codec initialization sequence includes 0x0e03. These must not be conflated without a live AVDTP trace.
- SSC's on-air media packet format: proprietary payload header, frame aggregation/fragmentation, RTP timestamps and scheduling.
- Dynamic bitrate algorithm beyond observed startup level change.
- Direct Windows A2DP playback from the Rust bridge and independent native x64 SSC encoder are NOT implemented.

## Local reproducibility
- ssc_live_profile.json: anonymized selected HAL config, UHQ2 flag, bitrate changes and SSC encoder events.
- ssc_live_encoder_2026-11-03.log: filtered non-Bluetooth-address SSC encoder log lines.
- ssc_live_report.py and test_ssc_live_report.py: sanitized reproducible log extraction and tests.
- ssc-win-bridge/examples/live_tone.rs: live-mode encoder exercise.
- ssc-win-bridge/src/transport.rs: conservative size checks; test covers 1005-byte MTU and both observed frame sizes.
- ssc_snoop.py: offline AVDTP parser for a future genuine HCI file.
- ghidra-bluetooth.log, ghidra-ssc-deep.log, ssc-bluetooth-full.c: static reverse engineering evidence.

## Verdict
SSC UHQ2 is positively confirmed as active at 96 kHz and 584 kbps, and its software encoder mode is reproducible on the Windows-to-Android bridge. **A Windows radio transmitter that sends SSC to the Buds remains unimplemented; no on-air frames have been validated.**
